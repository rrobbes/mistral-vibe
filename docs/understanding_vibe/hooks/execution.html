⚡ Exécution des Hooks

Comprenez comment les hooks sont exécutés, dans quel ordre, et comment ils interagissent avec le flux principal. Découvrez les mécanismes de timeout, d'erreur, et de chaîne de hooks.

🌊 Flux d'Exécution Global

📈 Timeline Complet avec Tous les Hooks

Voici le flux complet d'une conversation avec tous les hooks activés :

Étape 0 : Initialisation

Action : L'utilisateur envoie un message

Hooks : ❌ Aucun hook à ce stade

Étape 1 : Début du Tour

Action : Mistral Vibe prépare le tour de conversation

Hooks : ✅ POST_AGENT hooks (première exécution)

But : Injecter du contexte avant que le LLM ne génère sa réponse

ℹ️ Point clé : Si un hook POST_AGENT retourne "deny" avec une raison, cette raison est injectée comme message utilisateur et le LLM générera une nouvelle réponse.

Étape 2 : Génération LLM

Action : Le LLM génère une réponse (peut inclure des appels d'outils)

Hooks : ❌ Aucun hook pendant la génération

Étape 3 : Pour Chaque Appel d'Outil

Sous-étapes :

  1. PRE_TOOL hooks :
    • Exécutés dans l'ordre de configuration
    • Chaque hook peut :
      • ✅ "allow" : Continuer (avec éventuelle modification de tool_input)
      • ❌ "deny" : Bloquer l'exécution et arrêter la chaîne
    • Si un hook retourne "deny", les hooks suivants ne sont PAS exécutés
  2. Exécution de l'outil :
    • L'outil s'exécute avec les arguments éventuellement modifiés
  3. POST_TOOL hooks :
    • Exécutés dans l'ordre de configuration
    • Chaque hook peut :
      • ✅ "allow" : Continuer (avec éventuel additional_context)
      • ❌ "deny" : Remplacer la sortie par la reason + additional_context
    • Les modifications sont cumulatives : chaque hook peut ajouter son contexte
Étape 4 : Fin du Tour

Action : La réponse finale est préparée et affichée à l'utilisateur

Hooks : ✅ POST_AGENT hooks (deuxième exécution)

But : Notifier, auditer, déclencher des actions post-tour

Étape 5 : Attente Prochaine Requête

Action : Mistral Vibe attend la prochaine requête utilisateur

Hooks : ❌ Aucun hook

📋 Ordre d'Exécution des Hooks

🔄 Chaîne de Hooks

Lorsque plusieurs hooks du même type sont configurés, ils sont exécutés dans l'ordre de déclaration dans le fichier TOML.

Exemple : Chaîne de PRE_TOOL hooks 
[[hooks]]
name = "hook-1-validate"
type = "pre_tool"
command = "python3 hooks/validate.py"
match = "*"

[[hooks]]
name = "hook-2-transform"
type = "pre_tool"
command = "python3 hooks/transform.py"
match = "*"

[[hooks]]
name = "hook-3-audit"
type = "pre_tool"
command = "python3 hooks/audit.py"
match = "*"

Ordre d'exécution : hook-1-validate → hook-2-transform → hook-3-audit

1. hook-1-validate
Valide l'appel
→
2. hook-2-transform
Transforme l'input
→
3. hook-3-audit
Logger l'appel
→
4. Exécution
L'outil s'exécute

Si hook-1 retourne "deny", hook-2 et hook-3 ne sont PAS exécutés

🎯 Comportement par Type de Hook

🔵

POST_AGENT

Ordre : Dans l'ordre de déclaration

Comportement :

  • Chaque hook est exécuté indépendamment
  • Si un hook retourne "deny" :
    • Un message utilisateur est injecté
    • Le LLM régénérera une réponse
    • Les hooks suivants sont TOUJOURS exécutés

🔴

PRE_TOOL

Ordre : Dans l'ordre de déclaration, filtré par match

Comportement :

  • Chaque hook est exécuté dans l'ordre
  • Si un hook retourne "deny" :
    • L'exécution de l'outil est bloquée
    • Les hooks suivants ne sont PAS exécutés
    • La raison est retournée comme erreur
  • Si un hook retourne "allow" avec tool_input :
    • Les arguments sont mis à jour
    • Le hook suivant reçoit les arguments modifiés

🟢

POST_TOOL

Ordre : Dans l'ordre de déclaration, filtré par match

Comportement :

  • Chaque hook est exécuté dans l'ordre
  • Si un hook retourne "deny" :
    • La sortie est remplacée par la reason
    • Les hooks suivants sont TOUJOURS exécutés
    • Chaque hook peut ajouter son contexte
  • Si un hook retourne "allow" avec additional_context :
    • Le contexte est ajouté à la fin de la sortie
    • Le hook suivant reçoit la sortie avec le contexte ajouté

⚠️ Gestion des Erreurs et Timeouts

💥 Que se passe-t-il en cas d'erreur ?

Plusieurs types d'erreurs peuvent survenir pendant l'exécution d'un hook :

❌

Code de Sortie ≠ 0

Le processus du hook retourne un code d'erreur non nul.

Comportement :

  • Le hook est considéré comme échoué
  • Si strict=true : tratamiento selon le type
  • Si strict=false : warning + le hook est ignoré

⏱️

Timeout

Le hook prend plus de temps que le timeout configuré.

Comportement :

  • Le processus est tué
  • Le hook est considéré comme échoué
  • Si strict=true : traitement selon le type
  • Si strict=false : warning + le hook est ignoré

⚠️

Sortie Non-JSON

Le hook retourne une sortie qui n'est pas du JSON valide.

Comportement :

  • Le hook est considéré comme échoué
  • Si strict=true : traitement selon le type
  • Si strict=false : warning + le hook est ignoré

🚫

Échec du Démarrage

Impossible de démarrer le processus du hook (fichier introuvable, permission, etc.).

Comportement :

  • Le hook est considéré comme échoué
  • Un message d'erreur est affiché
  • Si strict=true : traitement selon le type
  • Si strict=false : warning + le hook est ignoré

🛡️ Mode Strict par Type de Hook

Voici ce qui se passe en mode strict=true pour chaque type de hook :

Type de Hook Comportement en strict=true Effet sur le Flux
POST_AGENT Le hook est considéré comme ayant retourné "deny" avec la raison de l'erreur Un retry est injecté avec la raison comme message utilisateur
PRE_TOOL Le hook retourne "deny" avec la raison de l'erreur L'exécution de l'outil est bloquée avec la raison comme erreur
POST_TOOL La sortie est remplacée par un message vide ou la raison La sortie de l'outil est effacée ou remplacée

⚠️ Attention : En mode strict, une erreur dans un hook bloque le flux normal.

  • POST_AGENT : Crée une boucle de retry
  • PRE_TOOL : Bloque l'outil
  • POST_TOOL : Efface la sortie
Utilisez strict=true uniquement pour des hooks critiques et bien testés.

⏰ Gestion des Timeouts

Chaque hook a un timeout configuré (par défaut : 60 secondes). Voici comment ça fonctionne :

1. Début
Hook commence
→
2. Timer Start
Timeout = 30s
→
3. Exécution
Le hook s'exécute...
→
4. Timeout ?
Temps écoulé ?
✅ Non
Hook termine normalement
↓
Récupérer Résultat
❌ Oui
Timeout atteint
↓
Tuer Processus
↓
Gérer Erreur

Choix du timeout :

  • timeout = 5 - Pour des hooks très simples (validation basique)
  • timeout = 15 - Pour des hooks moyens (transformation, logging)
  • timeout = 30 - Pour des hooks qui font des appels API
  • timeout = 60 - Par défaut, pour les hooks complexes

ℹ️ Astuce : Si votre hook fait des appels réseau, prévoyez un timeout plus long et gérez les timeouts dans votre code :

Gestion des timeouts en Python 
import json
import sys
import requests
from requests.exceptions import Timeout

try:
    # Timeout global : 25s (pour laisser 5s de marge)
    response = requests.get("https://api.example.com", timeout=25)
    # ... traiter la réponse ...
    print(json.dumps({"decision": "allow"}))
except Timeout:
    # Gérer le timeout proprement
    print(json.dumps({
        "decision": "allow",
        "system_message": "[API timeout - utilisant cache]"
    }))
except Exception as e:
    print(json.dumps({"decision": "allow"}))

sys.exit(0)

⚡ Optimisation des Performances

🎯 Bonnes Pratiques pour des Hooks Rapides

Les hooks s'exécutent de manière asynchrone mais peuvent ralentir votre workflow. Voici comment optimiser :

✅

Minimiser le Travail

  • Faites le strict minimum dans vos hooks
  • Évitez les calculs lourds
  • Déléguez le travail lourd à des systèmes externes

Exemple : Logger dans un fichier plutôt que dans une base de données

⚡

Utiliser le Matching

  • Utilisez le champ match pour filtrer
  • Évitez match = "*" si possible
  • Soyez spécifique dans vos patterns

Exemple : match = "bash" au lieu de match = "*"

🔄

Asynchrone Interne

  • Dans vos hooks, utilisez l'asynchrone si possible
  • Pour les appels réseau, utilisez aiohttp au lieu de requests

Exemple : Utiliser async/await dans vos hooks Python

📊

Cachez les Résultats

  • Cachez les résultats des appels API
  • Utilisez un cache local (Redis, fichier, etc.)
  • Rafraîchissez le cache en arrière-plan

Exemple : Cachez les appels à des APIs externes

🎯

Choisir le Bon Type

  • Utilisez le type de hook le plus adapté
  • POST_TOOL est souvent plus rapide que POST_AGENT
  • PRE_TOOL permet de bloquer tôt

Exemple : Utilisez PRE_TOOL pour la validation plutôt que POST_AGENT

📦

Langage Approprié

  • Utilisez le langage le plus performant
  • Python pour la simplicité
  • Bash pour les opérations simples
  • Rust/Go pour les hooks critiques

Exemple : Bash pour les hooks simples, Python pour les hooks complexes

⚠️ À Éviter

Voici ce qu'il faut éviter pour ne pas ralentir votre workflow :

❌

Appels Bloquants

Évitez les appels réseau synchrones longs sans timeout.

❌ À éviter 
# ❌ Mauvais : Pas de timeout, bloquant
response = requests.get("https://api.example.com")
✅ À faire 
# ✅ Bon : Avec timeout
response = requests.get("https://api.example.com", timeout=5)
❌

Boucles Infinies

Évitez les boucles infinies ou les appels récursifs sans limite.

❌ À éviter 
# ❌ Mauvais : Boucle sans limite
while True:
    # ... fait quelque chose ...
    pass
❌

Travail Lourd

Évitez les calculs lourds ou le traitement de gros fichiers.

❌ À éviter 
# ❌ Mauvais : Lecture de gros fichier
with open("/var/log/huge.log", "r") as f:
    content = f.read()  # Peut prendre des secondes
✅ À faire 
# ✅ Bon : Lecture ligne par ligne
with open("/var/log/huge.log", "r") as f:
    for line in f:
        # Traiter chaque ligne
        if "error" in line:
            break  # Arrêter tôt si possible
❌

strict=true Inutile

Évitez strict=true pour des hooks non critiques.

❌ À éviter 
[[hooks]]
name = "audit-log"
type = "post_tool"
command = "python3 hooks/log.py"
strict = true  # ❌ Inutile pour un hook de logging
✅ À faire 
[[hooks]]
name = "audit-log"
type = "post_tool"
command = "python3 hooks/log.py"
strict = false  # ✅ Correct pour un hook de logging
