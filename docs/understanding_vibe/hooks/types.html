🏷️ Les 3 Types de Hooks

Mistral Vibe propose 3 types de hooks distincts, chacun avec une finalité précise. Découvrez quand et comment utiliser chaque type pour répondre à vos besoins.

📚 Introduction aux Types de Hooks

🎯 Pourquoi 3 Types ?

Les 3 types de hooks correspondent aux 3 moments clés du cycle de vie de Mistral Vibe :

Timeline du Cycle de Vie

🔵 POST_AGENT
Après le tour LLM
→
🟠 LLM Génère Réponse
"J'appelle un outil"
→
🔴 PRE_TOOL
Avant l'exécution
↓
🔵 Exécution de l'outil
tool()
→
🟢 POST_TOOL
Après l'exécution
→
Réponse à l'Utilisateur
Affichage du résultat
↓
🔵 POST_AGENT
Après le tour complet

Résumé :

  1. POST_AGENT : Avant que l'utilisateur ne fasse une nouvelle requête (début du tour)
  2. LLM génère une réponse (peut inclure des appels d'outils)
  3. PRE_TOOL : Avant chaque appel d'outil
  4. L'outil s'exécute
  5. POST_TOOL : Après chaque appel d'outil
  6. Réponse finale à l'utilisateur
  7. POST_AGENT : Après le tour complet

📊 Comparaison Rapide

Type Quand Peut Bloquer Peut Modifier Use Case Principal
POST_AGENT Après un tour complet ✅ Oui (retry) ✅ Oui (contexte) Intégration, audit, contexte global
PRE_TOOL Avant un appel d'outil ✅ Oui (deny) ✅ Oui (tool_input) Sécurité, validation, modification
POST_TOOL Après un appel d'outil ✅ Oui (remplacement) ✅ Oui (sortie) Transformation, audit, intégration

🔵 POST_AGENT Hooks

📖 Définition

Les hooks POST_AGENT sont exécutés après chaque tour complet de conversation. Un "tour" correspond à :

  1. L'utilisateur envoie un message
  2. Le LLM génère une réponse
  3. Les outils éventuels sont exécutés
  4. La réponse finale est affichée

⚠️ Point important : Les hooks POST_AGENT s'exécutent 2 fois par tour :

  1. Avant que le LLM ne génère sa réponse (pour éventuellement injecter du contexte)
  2. Après que le tour soit complet

🎯 Cas d'Usage

Les hooks POST_AGENT sont parfaits pour :

🔄

Intégration Externe

Notifier des systèmes externes (Slack, Discord, email, etc.) qu'une action a été effectuée.

Exemple : "Envoyer une notification Slack après chaque requête"

📊

Audit Global

Journaliser toutes les conversations ou actions à un niveau global.

Exemple : "Écrire un log complet de la session dans un fichier central"

🧠

Enrichissement du Contexte

Ajouter automatiquement des informations contextuelles (date, utilisateur, projet, etc.).

Exemple : "Injecter la date du jour et le nom de l'utilisateur dans le contexte"

⚡

Automatisation Post-Tour

Déclencher des actions automatiques après chaque interaction.

Exemple : "Sauvegarder automatiquement les fichiers modifiés"

📥 Données Reçues (PostAgentInvocation)

Le hook POST_AGENT reçoit une structure PostAgentInvocation contenant :

Structure PostAgentInvocation 
{
  "hook_event_name": "post_agent",
  "session_id": "session_abc123",
  "transcript_path": "/home/user/.vibe/sessions/session_abc123/transcript.json",
  "cwd": "/home/user/project",
  "parent_session_id": null
}

Champs disponibles :

  • session_id - ID unique de la session
  • transcript_path - Chemin vers le fichier de transcript
  • cwd - Répertoire de travail courant
  • parent_session_id - ID de la session parente (si applicable)

⚠️ Limitation : Les hooks POST_AGENT n'ont pas accès :

  • À la requête utilisateur
  • À la réponse du LLM
  • Aux résultats des outils
Si vous avez besoin de ces informations, utilisez plutôt PRE_TOOL ou POST_TOOL.

📤 Réponses Possibles

Un hook POST_AGENT peut retourner différentes réponses selon ce qu'il veut faire :

✅ Allow (Par défaut)

Le tour continue normalement. Vous pouvez optionnellement ajouter un message système.

Allow simple 
{
  "decision": "allow"
}
Allow avec message 
{
  "decision": "allow",
  "system_message": "Contexte ajouté : Aujourd'hui est le 2 nov. 2024"
}

❌ Deny (Injecter un Retry)

Le hook peut injecter un message utilisateur pour déclencher un retry. Utile pour demander des clarifications ou corriger une requête.

Nombre de retries maximum : 3 par hook par tour

Deny avec message de retry 
{
  "decision": "deny",
  "reason": "Veuillez préciser le chemin du fichier"
}

Résultat : L'agent recevra le message "Veuillez préciser le chemin du fichier" comme s'il venait de l'utilisateur, et générera une nouvelle réponse.

🎯 Exemples Concrets

📊 Audit : Journaliser dans un fichier

hook_post_agent_audit.py 
#!/usr/bin/env python3
import json
import sys
from datetime import datetime
from pathlib import Path

invocation = json.load(sys.stdin)

# Journaliser dans un fichier
log_file = Path("~/vibe_audit.log").expanduser()
log_entry = {
    "timestamp": datetime.now().isoformat(),
    "hook": "post_agent_audit",
    "session_id": invocation.get("session_id"),
    "cwd": invocation.get("cwd")
}

log_file.write_text(
    json.dumps(log_entry) + "\n",
    append=True
)

print(json.dumps({"decision": "allow"}))
sys.exit(0)

💬 Contexte : Ajouter des infos utilisateur

hook_post_agent_context.py 
#!/usr/bin/env python3
import json
import sys
import socket
from datetime import datetime

invocation = json.load(sys.stdin)

# Construire un message de contexte
context = f"""
--- Contexte Automatique ---
Date : {datetime.now().strftime('%Y-%m-%d %H:%M:%S')}
Machine : {socket.gethostname()}
Session : {invocation.get('session_id', 'unknown')}
Répertoire : {invocation.get('cwd', 'unknown')}
"""

print(json.dumps({
    "decision": "allow",
    "system_message": context
}))
sys.exit(0)

🔗 Intégration : Notifier Slack

hook_post_agent_slack.py 
#!/usr/bin/env python3
import json
import sys
import requests
import os

invocation = json.load(sys.stdin)

webhook_url = os.getenv("SLACK_WEBHOOK_URL")
if not webhook_url:
    print(json.dumps({"decision": "allow"}))
    sys.exit(0)

message = {
    "text": f"✅ Mistral Vibe a terminé un tour (Session: {invocation.get('session_id')})"
}

try:
    requests.post(webhook_url, json=message, timeout=5)
except:
    pass  # Ne pas bloquer l'agent

print(json.dumps({"decision": "allow"}))
sys.exit(0)

🔴 PRE_TOOL Hooks

📖 Définition

Les hooks PRE_TOOL sont exécutés avant chaque appel d'outil. Ils permettent de :

  • Valider que l'appel d'outil est autorisé
  • Modifier les arguments de l'outil avant exécution
  • Bloquer complètement l'exécution de l'outil

✨ Point clé : Les hooks PRE_TOOL sont séquentiels et bloquants. Si un hook retourne "deny", les hooks suivants ne sont PAS exécutés.

🎯 Cas d'Usage

Les hooks PRE_TOOL sont parfaits pour :

🔒

Sécurité

Bloquer l'exécution d'outils ou de commandes dangereuses.

Exemple : "Empêcher l'exécution de rm -rf"

✅

Validation

Valider que les arguments respectent vos règles métier.

Exemple : "Vérifier que les paths sont valides"

🔄

Transformation

Modifier les arguments avant exécution.

Exemple : "Ajouter automatiquement des flags à une commande"

📝

Audit Préventif

Journaliser avant l'exécution pour l'audit.

Exemple : "Logger qu'un outil va être exécuté"

📥 Données Reçues (PreToolInvocation)

Le hook PRE_TOOL reçoit une structure PreToolInvocation contenant :

Structure PreToolInvocation 
{
  "hook_event_name": "pre_tool",
  "session_id": "session_abc123",
  "transcript_path": "/home/user/.vibe/sessions/session_abc123/transcript.json",
  "cwd": "/home/user/project",
  "parent_session_id": null,
  "tool_name": "bash",
  "tool_call_id": "call_xyz789",
  "tool_input": {
    "command": "ls -la"
  }
}

Champs disponibles :

  • tool_name - Nom de l'outil qui va être appelé
  • tool_call_id - ID unique de cet appel d'outil
  • tool_input - Arguments passés à l'outil (dict)
  • + Tous les champs HookSessionContext

📤 Réponses Possibles

Un hook PRE_TOOL peut retourner différentes réponses :

✅ Allow (Autoriser)

L'outil peut être exécuté. Vous pouvez optionnellement modifier les arguments.

Allow simple 
{
  "decision": "allow"
}
Allow avec modification 
{
  "decision": "allow",
  "hook_specific_output": {
    "tool_input": {
      "command": "ls -la --color=always"
    }
  }
}

Effet : L'outil sera appelé avec command = "ls -la --color=always" au lieu de "ls -la".

❌ Deny (Bloquer)

L'outil est bloqué et ne sera PAS exécuté. La raison est retournée comme erreur.

Deny avec raison 
{
  "decision": "deny",
  "reason": "Commande 'rm -rf' interdite"
}

Effet : L'utilisateur verra l'erreur "Commande 'rm -rf' interdite" et l'outil ne sera pas exécuté.

🎯 Exemples Concrets

🔒 Sécurité : Bloquer rm -rf

hook_pre_tool_block_rm_rf.py 
#!/usr/bin/env python3
import json
import sys

invocation = json.load(sys.stdin)

# Vérifier si c'est un appel bash
if invocation.get("tool_name") == "bash":
    command = invocation.get("tool_input", {}).get("command", "")
    
    # Bloquer les commandes dangereuses
    dangerous = ["rm -rf", "rm -r", ":(){ :|:& };:"]
    if any(d in command for d in dangerous):
        print(json.dumps({
            "decision": "deny",
            "reason": f"Commande dangereuse détectée : {command[:30]}"
        }))
        sys.exit(0)

# Autoriser par défaut
print(json.dumps({"decision": "allow"}))
sys.exit(0)

✅ Validation : Vérifier les paths

hook_pre_tool_validate_paths.py 
#!/usr/bin/env python3
import json
import sys
from pathlib import Path

invocation = json.load(sys.stdin)

# Vérifier read_file et write_file
if invocation.get("tool_name") in ["read_file", "write_file"]:
    path = invocation.get("tool_input", {}).get("path", "")
    
    # Bloquer l'accès en dehors du répertoire de travail
    cwd = invocation.get("cwd", "/")
    full_path = Path(path).resolve()
    cwd_path = Path(cwd).resolve()
    
    if not str(full_path).startswith(str(cwd_path)):
        print(json.dumps({
            "decision": "deny",
            "reason": f"Accès interdit en dehors de {cwd}"
        }))
        sys.exit(0)

print(json.dumps({"decision": "allow"}))
sys.exit(0)

🔄 Transformation : Ajouter --color=always

hook_pre_tool_add_colors.py 
#!/usr/bin/env python3
import json
import sys

invocation = json.load(sys.stdin)

# Ajouter --color=always aux commandes ls
if invocation.get("tool_name") == "bash":
    command = invocation.get("tool_input", {}).get("command", "")
    
    if command.strip().startswith("ls"):
        # Ajouter --color=always si pas déjà présent
        if "--color" not in command:
            new_command = command.replace("ls", "ls --color=always")
            print(json.dumps({
                "decision": "allow",
                "hook_specific_output": {
                    "tool_input": {"command": new_command}
                }
            }))
            sys.exit(0)

print(json.dumps({"decision": "allow"}))
sys.exit(0)

🟢 POST_TOOL Hooks

📖 Définition

Les hooks POST_TOOL sont exécutés après chaque appel d'outil. Ils permettent de :

  • Transformer la sortie de l'outil avant qu'elle ne soit envoyée au LLM
  • Journaliser les résultats des outils
  • Remplacer complètement la sortie
  • Ajouter du contexte à la sortie

✨ Point clé : Les hooks POST_TOOL peuvent modifier la sortie visible par le LLM. Cela permet de :

  • Nettoyer des données sensibles
  • Formater les sorties
  • Ajouter des métadonnées
  • Remplacer complètement le résultat

🎯 Cas d'Usage

Les hooks POST_TOOL sont parfaits pour :

🔄

Transformation

Modifier la sortie avant qu'elle ne soit vue par le LLM.

Exemple : "Ajouter un timestamp à toutes les sorties"

📊

Audit

Journaliser les résultats des outils.

Exemple : "Logger le résultat de chaque appel d'outil"

🔒

Nettoyage

Nettoyer ou filtrer des données sensibles.

Exemple : "Masquer les mots de passe dans les sorties"

🔗

Intégration

Déclencher des actions basées sur les résultats.

Exemple : "Envoyer une notification si un outil échoue"

📥 Données Reçues (PostToolInvocation)

Le hook POST_TOOL reçoit une structure PostToolInvocation contenant :

Structure PostToolInvocation 
{
  "hook_event_name": "post_tool",
  "session_id": "session_abc123",
  "transcript_path": "/home/user/.vibe/sessions/session_abc123/transcript.json",
  "cwd": "/home/user/project",
  "parent_session_id": null,
  "tool_name": "read_file",
  "tool_call_id": "call_xyz789",
  "tool_input": {
    "path": "/home/user/file.txt"
  },
  "tool_status": "success",
  "tool_output": {
    "content": "Contenu du fichier...",
    "path": "/home/user/file.txt"
  },
  "tool_output_text": "Contenu du fichier...",
  "tool_error": null,
  "duration_ms": 125.5
}

Champs disponibles :

  • tool_name - Nom de l'outil qui a été appelé
  • tool_call_id - ID unique de cet appel d'outil
  • tool_input - Arguments passés à l'outil
  • tool_status - "success", "failure", ou "cancelled"
  • tool_output - Résultat structuré de l'outil (dict ou None)
  • tool_output_text - Texte brut de la sortie (ce qui sera envoyé au LLM)
  • tool_error - Message d'erreur si tool_status == "failure"
  • duration_ms - Durée d'exécution en millisecondes

📤 Réponses Possibles

Un hook POST_TOOL peut retourner différentes réponses :

✅ Allow (Autoriser)

La sortie est acceptée telle quelle. Vous pouvez optionnellement ajouter du contexte.

Allow simple 
{
  "decision": "allow"
}
Allow avec contexte ajouté 
{
  "decision": "allow",
  "hook_specific_output": {
    "additional_context": "\n[Fichier lu avec succès]"
  }
}

Effet : Le texte "[Fichier lu avec succès]" sera ajouté à la fin de la sortie.

❌ Deny (Remplacer)

La sortie est remplacée par la raison. Le champ additional_context permet d'ajouter du texte après la raison.

Deny avec remplacement 
{
  "decision": "deny",
  "reason": "[Contenu masqué pour raisons de sécurité]",
  "hook_specific_output": {
    "additional_context": "\nLe fichier contenait des informations sensibles."
  }
}

Effet : La sortie sera remplacée par :
[Contenu masqué pour raisons de sécurité]\nLe fichier contenait des informations sensibles.

🎯 Exemples Concrets

🔄 Transformation : Ajouter timestamp

hook_post_tool_add_timestamp.py 
#!/usr/bin/env python3
import json
import sys
from datetime import datetime

invocation = json.load(sys.stdin)

# Ajouter un timestamp à la sortie
timestamp = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
additional = f"\n---\n[Generé le {timestamp}]"

print(json.dumps({
    "decision": "allow",
    "hook_specific_output": {
        "additional_context": additional
    }
}))
sys.exit(0)

🔒 Sécurité : Masquer les secrets

hook_post_tool_mask_secrets.py 
#!/usr/bin/env python3
import json
import sys
import re

invocation = json.load(sys.stdin)

# Masquer les mots de passe et tokens
output_text = invocation.get("tool_output_text", "")
secrets = ["password", "secret", "token", "api_key"]

for secret in secrets:
    output_text = re.sub(
        rf'{secret}\s*[=:]\s*[\"\']?([^\s\"\']+)[\"\']?',
        f'{secret}=[MASKED]',
        output_text,
        flags=re.IGNORECASE
    )

print(json.dumps({
    "decision": "deny",
    "reason": output_text,
    "hook_specific_output": {
        "additional_context": "\n[Secrets masqués]"
    }
}))
sys.exit(0)

📊 Audit : Journaliser les erreurs

hook_post_tool_log_errors.py 
#!/usr/bin/env python3
import json
import sys
from pathlib import Path
from datetime import datetime

invocation = json.load(sys.stdin)

# Ne logger que les erreurs
if invocation.get("tool_status") == "failure":
    log_file = Path("~/vibe_errors.log").expanduser()
    log_entry = {
        "timestamp": datetime.now().isoformat(),
        "session_id": invocation.get("session_id"),
        "tool_name": invocation.get("tool_name"),
        "tool_error": invocation.get("tool_error"),
        "tool_input": invocation.get("tool_input")
    }
    log_file.write_text(
        json.dumps(log_entry) + "\n",
        append=True
    )

# Toujours retourner allow
print(json.dumps({"decision": "allow"}))
sys.exit(0)

📊 Résumé Comparatif des 3 Types

Critère POST_AGENT PRE_TOOL POST_TOOL
Quand Après un tour complet Avant un appel d'outil Après un appel d'outil
Fréquence 2x par tour (avant/après LLM) 1x par outil appelé 1x par outil appelé
Peut bloquer ✅ Oui (retry) ✅ Oui (deny) ✅ Oui (remplacement)
Peut modifier input ❌ Non ✅ Oui (tool_input) ❌ Non
Peut modifier output ❌ Non ❌ Non ✅ Oui (additional_context)
Accès à la requête LLM ❌ Non ❌ Non ❌ Non
Accès à tool_input ❌ Non ✅ Oui ✅ Oui
Accès à tool_output ❌ Non ❌ Non ✅ Oui
Use case principal Intégration, contexte global Sécurité, validation, modification Transformation, audit, nettoyage
Use case secondaire Audit global, notification Audit préventif Intégration basée sur résultat

💡 Conseil pour bien choisir :

  • POST_AGENT : "Je veux faire quelque chose après chaque conversation"
  • PRE_TOOL : "Je veux valider ou modifier avant qu'un outil ne s'exécute"
  • POST_TOOL : "Je veux transformer ou auditer après qu'un outil s'est exécuté"
Un même use case peut nécessiter plusieurs types de hooks !
