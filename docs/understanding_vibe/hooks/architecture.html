🏗️ Architecture du Système de Hooks

Plongez dans les entrailles du système de hooks pour comprendre comment chaque composant interagit. Découvrez le flux de données, les responsabilités de chaque module, et comment tout s'assemble.

📊 Vue d'Ensemble de l'Architecture

🎯 Principles de Conception

Le système de hooks de Mistral Vibe a été conçu selon plusieurs principes clés :

🔌

Découplage Total

Les hooks sont complètement découplés du code core. Ils s'exécutent dans des processus séparés.

📦

Communication Standardisée

Tout passe par JSON sur stdin/stdout. N'importe quel langage peut implémenter un hook.

⚡

Asynchrone & Non-Bloquant

Les hooks s'exécutent de manière asynchrone avec des timeouts. Un hook lent ne bloque pas l'agent.

🛡️

Sécurité par Défaut

Isolation des processus, validation des entrées/sorties, limites de taille et de temps.

📁 Structure des Fichiers

Voici où se trouvent les différents composants dans le codebase : 

vibe/
├── core/
│   ├── hooks/
│   │   ├── __init__.py          # Exports publics
│   │   ├── models.py            # 📊 Structures de données (Pydantic)
│   │   ├── config.py            # 📄 Chargement des fichiers TOML
│   │   ├── manager.py           # 🎭 Orchestrateur principal
│   │   ├── executor.py          # ⚡ Exécuteur de processus
│   │   ├── _handler.py          # 🎚️ Handler base abstrait
│   │   ├── _pre_tool.py         # 🔴 Handler PRE_TOOL
│   │   ├── _post_tool.py        # 🟢 Handler POST_TOOL
│   │   └── _post_agent.py       # 🔵 Handler POST_AGENT
│   └── agent_loop_hooks.py     # 🔄 Mixin pour l'agent loop
└── ...

💡 Note : Les fichiers préfixés par _ sont des modules internes (private). Seuls les exports dans __init__.py font partie de l'API publique.

🧩 Composants Principaux

Étape 1 : Configuration

📄 config.py

Rôle : Charger et parser les fichiers de configuration TOML.

Fonctions clés :

  • load_hooks_file(path) - Charge un fichier TOML
  • load_hooks_from_fs() - Charge tous les fichiers de hooks

Retourne : HookConfigResult avec la liste des hooks et les erreurs éventuelles.

Exemple de structure TOML 
[[hooks]]
name = "my-pre-tool-hook"
type = "pre_tool"
command = "python3 /path/to/my_hook.py"
match = "bash"
timeout = 30
strict = true

[[hooks]]
name = "my-post-agent-hook"
type = "post_agent"
command = "node /path/to/another_hook.js"
timeout = 10
Étape 2 : Définition des Modèles

📊 models.py

Rôle : Définir les structures de données et les types pour tout le système.

Classes principales :

  • HookType - Enum : POST_AGENT, PRE_TOOL, POST_TOOL
  • HookConfig - Configuration d'un hook depuis TOML
  • HookInvocation - Données passées au hook (3 sous-types)
  • HookStructuredResponse - Réponse attendue du hook
  • HookExecutionResult - Résultat de l'exécution

✨ Bon à savoir : Toutes les structures utilisent Pydantic pour la validation automatique et la sérialisation JSON.

Étape 3 : Exécution des Processus

⚡ executor.py

Rôle : Exécuter les hooks comme des sous-processus asynchrones.

Classe principale : HookExecutor

Mécanisme :

  1. Créer un processus avec asyncio.create_subprocess_shell()
  2. Écrire les données d'invocation sur stdin en JSON
  3. Lire la sortie sur stdout (attendue en JSON)
  4. Gérer les erreurs et les timeouts

⚠️ Important :

  • Le hook doit retourner un code de sortie 0 pour succès
  • La sortie doit être du JSON valide sur stdout
  • Les erreurs vont sur stderr (non interprétées)
  • Timeout par défaut : 60 secondes

Flux d'exécution simplifié 
async def run(hook: HookConfig, invocation: HookInvocation):
    # 1. Créer le processus
    process = await asyncio.create_subprocess_shell(
        hook.command,
        stdin=PIPE, stdout=PIPE, stderr=PIPE
    )
    
    # 2. Envoyer l'invocation en JSON
    stdin_data = invocation.model_dump_json().encode()
    await process.stdin.write(stdin_data)
    
    # 3. Attendre la réponse avec timeout
    stdout, stderr = await asyncio.wait_for(
        self._run_process(process, stdin, stdin_data),
        timeout=hook.timeout
    )
    
    # 4. Retourner le résultat
    return HookExecutionResult(
        hook_name=hook.name,
        exit_code=process.returncode,
        stdout=stdout.decode(),
        stderr=stderr.decode(),
        timed_out=False
    )
Étape 4 : Traitement des Réponses

🎚️ _handler.py + Handlers Spécifiques

Rôle : Interpréter les réponses des hooks et prendre des décisions.

Architecture :

  • HookHandler - Classe abstraite base
  • PreToolHandler - Gère les hooks PRE_TOOL
  • PostToolHandler - Gère les hooks POST_TOOL
  • PostAgentHandler - Gère les hooks POST_AGENT

Mécanisme de décision :

  1. Parser la sortie JSON → HookStructuredResponse
  2. Vérifier le champ decision : "allow" ou "deny"
  3. Appliquer les actions spécifiques selon le type de hook

❌ Si decision = "deny"

  • PRE_TOOL : Bloque l'exécution de l'outil
  • POST_TOOL : Remplace le texte de sortie
  • POST_AGENT : Injecte un message utilisateur (retry)

✅ Si decision = "allow"

  • PRE_TOOL : Peut modifier tool_input
  • POST_TOOL : Peut ajouter du contexte
  • POST_AGENT : Poursuit normalement
Étape 5 : Orchestration

🎭 manager.py + agent_loop_hooks.py

Rôle : Coordonner l'exécution des hooks dans le bon ordre et au bon moment.

HooksManager (manager.py) :

  • Gère une liste de HookConfig
  • Filtre les hooks par type et par match
  • Exécute les hooks dans l'ordre de configuration
  • Gère le strict mode et les retries

AgentLoopHooksMixin (agent_loop_hooks.py) :

  • Intègre les hooks dans l'AgentLoop
  • Fournit les méthodes :
    • _run_pre_tool_hooks()
    • _run_post_tool_hooks()
    • _run_post_agent_hooks()
  • Construit le HookSessionContext

🔗 Connexion : Le HooksManager est instancié dans l'AgentLoop avec la liste des hooks chargés depuis la configuration.

🌊 Flux de Données

📥 Données d'Entrée (HookInvocation)

Chaque hook reçoit une structure HookInvocation qui contient :

🔵 HookSessionContext

Commun à tous les types de hooks :

  • session_id - ID de la session
  • transcript_path - Chemin du fichier de transcript
  • cwd - Répertoire de travail
  • parent_session_id - ID de la session parente

⚪ POST_AGENT (PostAgentInvocation)

Exécuté après chaque tour de conversation :

  • hook_event_name = "post_agent"

🔴 PRE_TOOL (PreToolInvocation)

Exécuté avant un appel d'outil :

  • tool_name - Nom de l'outil
  • tool_call_id - ID unique de l'appel
  • tool_input - Arguments de l'outil (dict)

🟢 POST_TOOL (PostToolInvocation)

Exécuté après un appel d'outil :

  • tool_name - Nom de l'outil
  • tool_call_id - ID unique de l'appel
  • tool_input - Arguments passés à l'outil
  • tool_status - "success", "failure", ou "cancelled"
  • tool_output - Résultat de l'outil (dict ou None)
  • tool_output_text - Texte brut de la sortie
  • tool_error - Erreur si présente
  • duration_ms - Durée d'exécution en ms
Exemple de PreToolInvocation en JSON 
{
  "hook_event_name": "pre_tool",
  "session_id": "session_abc123",
  "transcript_path": "/home/user/.vibe/sessions/session_abc123/transcript.json",
  "cwd": "/home/user/project",
  "parent_session_id": null,
  "tool_name": "bash",
  "tool_call_id": "call_xyz789",
  "tool_input": {
    "command": "ls -la"
  }
}

📤 Données de Sortie (HookStructuredResponse)

Le hook doit retourner un JSON avec cette structure (ou un sous-ensemble) :

Champ Type Valeur par défaut Description
decision "allow" | "deny" "allow" Autoriser ou bloquer l'action
reason string | null null Raison du deny (obligatoire si decision=deny)
system_message string | null null Message système à afficher
hook_specific_output object | null {} Output spécifique selon le type

hook_specific_output peut contenir :

  • tool_input (PRE_TOOL seulement) - Remplace les arguments de l'outil
  • additional_context (POST_TOOL seulement) - Texte à ajouter à la sortie
Exemples de réponses

✅ Allow par défaut

{
  "decision": "allow"
}

❌ Deny avec raison

{
  "decision": "deny",
  "reason": "Commande interdite"
}

🔄 PRE_TOOL : Modifier input

{
  "decision": "allow",
  "hook_specific_output": {
    "tool_input": {
      "command": "ls -la --color=always"
    }
  }
}

📝 POST_TOOL : Ajouter contexte

{
  "decision": "allow",
  "hook_specific_output": {
    "additional_context": "\n---\n[Hook: audit logged]"
  }
}

📊 Diagramme de Séquence

Voici comment les hooks s'intègrent dans le cycle de vie de Mistral Vibe :

📊 Flux Complet avec Hooks

Étape 1 : Requête Utilisateur "Ouvre le fichier"
Étape 2 : LLM Génère Réponse "J'appelle read_file"
✅ Étape 2b : POST_AGENT Hooks (Optionnel - Injection de contexte)
Étape 3 : Résolution de l'outil read_file("fichier.txt")
🔴 Étape 3b : PRE_TOOL Hooks Vérification/Modification des arguments
Étape 4 : Exécution de l'outil read_file s'exécute réellement
Étape 5 : Résultat de l'outil Contenu du fichier
🟢 Étape 5b : POST_TOOL Hooks Transformation/Journalisation de la sortie
Étape 6 : Réponse Finale Affichage à l'utilisateur
Étape 7 : Fin du Tour Mise à jour du contexte
🔵 Étape 7b : POST_AGENT Hooks (Optionnel - Audit, notification, etc.)

ℹ️ Points clés :

  • Les POST_AGENT hooks s'exécutent 2 fois : avant la génération LLM et après le tour complet
  • Les PRE_TOOL et POST_TOOL hooks sont spécifiques aux appels d'outils
  • Un hook peut bloquer (deny) ou modifier (allow + transformation) le flux
  • Les hooks sont exécutés dans l'ordre de configuration
