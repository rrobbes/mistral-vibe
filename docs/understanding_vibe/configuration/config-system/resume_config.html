01 — Introduction

Vue d'ensemble

Le système de configuration de Vibe repose sur une architecture en couches, pilotée par un schéma et fondée sur des snapshots. Chaque couche apporte une configuration partielle. Le résultat est fusionné puis validé avant d'être utilisé.

01. Couches

Plusieurs sources indépendantes fournissent des dictionnaires de configuration partiels.

02. Builder

Le ConfigBuilder fusionne les couches selon une stratégie définie pour chaque champ et valide le résultat.

03. Snapshot

La configuration finale est un modèle Pydantic gelé : on le remplace plutôt que de le modifier directement.

04. Orchestrator

Le ConfigOrchestrator centralise les modifications, les rechargements et les notifications.

Idée centrale : les couches restent séparées, mais l'application utilise une configuration consolidée et validée.
02 — Architecture

Les couches de configuration

L'ordre est défini dans build_default_orchestrator(). Plus une couche est placée bas dans la pile, plus sa priorité est élevée. Attention : cette règle dépend aussi de la stratégie de fusion du champ.

06 — Fonctionnement

  
Cycle de vie de la configuration

  

    La configuration est construite au démarrage, puis remplacée
    lorsqu'une modification est appliquée.
  

  

    
1. Création des couches

      Les sources utilisateur et projet sont ajoutées si elles sont activées.

    
2. Migrations

      migrate_config_layers(layers) applique les migrations.

    
3. Construction

      ConfigOrchestrator.create() appelle le builder et produit
      le premier snapshot.

    
4. Modification

      apply_patch() vérifie le patch et prépare une prévisualisation.

    
5. Écriture

      Les couches ciblées appliquent leurs opérations.

    
6. Rechargement

      Le builder reconstruit la configuration à partir des couches.

    
7. Notification

      L'EventBus publie un événement si une écriture a réussi et si des clés
      ont changé.

  

  

    Les écritures entre plusieurs couches ne sont pas atomiques.
    Une erreur d'écriture peut être retournée pour une couche sans annuler
    les écritures réussies sur les autres.
  






  
07 — Stockage

  
Persistance et concurrence

  

    

      
Fichiers TOML

      
Lecture avec tomllib, écriture avec tomli_w.
      Les opérations de lecture sont exécutées avec
      asyncio.to_thread.

    

    

      
Écriture atomique

      
Un fichier temporaire est créé dans le même dossier, écrit,
      synchronisé puis renommé pour remplacer le fichier cible.

    

    

      
Fingerprints

      
Les empreintes permettent de détecter les changements concurrents
      et d'éviter d'écraser silencieusement une modification externe.

    

    

      
Conflits

      
La stratégie par défaut est CANCEL : une empreinte différente
      déclenche une erreur de concurrence.

    

  

  
Étapes de l'écriture atomique

  
1. Création du fichier temporaire
2. Sérialisation TOML
3. flush() et fsync()
4. Calcul du fingerprint
5. Renommage atomique vers le fichier cible






  
08 — Sécurité

  
Sécurité et contrôle de confiance


  

    Le système de configuration de Mistral Vibe intègre plusieurs
    mécanismes destinés à contrôler l'origine des paramètres,
    protéger les informations sensibles et éviter les modifications
    non maîtrisées.
  


  

    

      Trust management
      
1. Confiance des configurations projet

      

        Une configuration de projet n'est pas automatiquement considérée
        comme fiable. Le système vérifie si le dossier appartient au
        trust store.
      

      

        Si le fichier existe dans un dossier non fiable, la couche
        ProjectConfigLayer n'est pas utilisée.
      

      
    


    

      Protection des credentials
      
2. Protection des URL sensibles

      

        AgentProfileLayer retire certains champs protégés, notamment
        les URL utilisées pour communiquer avec les services Vibe.
      

      

        Cela évite qu'un profil provenant d'un dépôt non fiable
        redirige les requêtes contenant une clé API vers un serveur
        contrôlé par un attaquant.
      

      
    


    

      Admin configuration
      
3. Priorité administrateur

      

        AdminConfigLayer est la couche de priorité la plus élevée.
        Cette position permet à l'organisation d'imposer certains
        paramètres de configuration.
      

      

        La priorité de cette couche constitue le mécanisme
        d'application des paramètres administrateur.
      

      
    


    

      Validation
      
4. Validation des données

      

        Le ConfigBuilder valide la configuration fusionnée avec
        le schéma Pydantic. Les erreurs de structure sont transformées
        en messages compréhensibles.
      

      

        Les couches peuvent également appliquer une validation
        à travers leur output_schema.
      

      
    


    

      Concurrency control
      
5. Protection contre les conflits

      

        Les fingerprints permettent de détecter si les données
        ont changé depuis la création d'un patch.
      

      

        Avec ConflictStrategy.CANCEL, une modification concurrente
        provoque une erreur plutôt qu'un écrasement silencieux.
      

      
    


    

      Storage
      
6. Écriture atomique

      

        Les fichiers TOML sont écrits dans un fichier temporaire,
        synchronisés puis renommés pour remplacer le fichier cible.
      

      

        Cette procédure réduit le risque de laisser un fichier
        de configuration partiellement écrit.

    À retenir : la sécurité repose sur plusieurs
    mécanismes complémentaires : contrôle de confiance, protection
    de champs sensibles, validation des données et gestion des conflits.
    Aucun de ces mécanismes ne doit être considéré isolément comme
    une garantie de sécurité complète.
  






  
09 — Conclusion

  
Principes de conception

  

    
Single source of truth

      
Un orchestrateur par session, détenu par l'app server.

    
Validation explicite

      
Chaque champ déclare sa stratégie de fusion.

    
Snapshots immuables

      
La configuration est remplacée plutôt que modifiée directement.

    
Concurrence optimiste

      
Les fingerprints détectent les modifications concurrentes.

    
Sécurité

      
Les couches non fiables sont ignorées et certaines valeurs sensibles
      sont protégées.

    
Compatibilité

      
Les migrations et les formats historiques sont pris en charge.
