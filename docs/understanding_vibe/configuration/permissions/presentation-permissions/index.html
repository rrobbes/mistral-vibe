Système de permissions de Mistral Vibe

Le système demande la permission avant toute action à risque.

Permissions

ALWAYS

Explication : L'outil s'exécute sans demander.

Exemple : Lire un fichier dans son dossier de projet.

NEVER

Explication : L'outil est toujours bloqué.

Exemple : Désactiver complètement les commandes bash.

ASK

Explication : L'outil demande avant de s'exécuter.

Exemple : Écrire un fichier ou lancer une commande.

allowlist

Explication : Liste des actions toujours autorisées.

Exemple : git status ou ls peuvent être autorisés.

denylist

Explication : Liste des actions toujours bloquées.

Exemple : sudo ou rm -rf / sont bloqués.

Fichiers sensibles

Explication : Fichiers avec des secrets. Toujours une demande.

Exemple : .env ou .ssh/.

Règles temporaires/permanentes

Explication : Autoriser une fois, pour la session, ou toujours.

Exemple : Cliquer sur « Always allow » dans la fenêtre.

Workspace

Explication : Dossier du projet. Hors workspace = demande.

Exemple : Lire /etc/passwd demande confirmation.

Permissions vs isolation

Explication : Demander la permission vs bloquer techniquement.

Exemple : Pas de cage technique. Juste un vigile.

Lecture dans le workspace

Comment ça se passe : L'agent veut lire un fichier dans son dossier. Il peut le faire sans demander.

Écriture dans le workspace

Comment ça se passe : L'agent veut écrire un fichier. Il doit demander la permission.

Accès hors workspace

Comment ça se passe : L'agent veut lire un fichier hors de son dossier. Il doit demander la permission.

Fichier .env

Comment ça se passe : L'agent veut lire un fichier avec des secrets. Il doit demander, même si tout est autorisé.

Commande allowlistée

Comment ça se passe : L'agent veut lancer git status. Il peut le faire sans demander.

Commande denylistée

Comment ça se passe : L'agent veut lancer sudo. Il doit demander la permission.

Commande avec sudo

Comment ça se passe : L'agent veut utiliser sudo. Il doit demander la permission.

Permission déjà accordée

Comment ça se passe : L'utilisateur a déjà autorisé cette action. L'agent peut l'exécuter.

Refus (Deny ou Esc)

Comment ça se passe : L'utilisateur dit non ou appuie sur Échap. L'action est annulée. L'agent continue son travail.

En cas de refus ?

L'agent reçoit : Un message d'erreur indiquant que l'action est refusée.

L'agent continue : Oui, il passe à l'étape suivante. Journalisé : Oui, dans les logs (_loop.py:L2863-2868)

Mots nouveaux

permission
Autoriser ou refuser une action.
Exemple : Comme un vigile qui contrôle l'entrée.
workspace
Dossier du projet où l'agent travaille.
Exemple : Comme un bureau où tout est autorisé.
allowlist
Liste des actions toujours autorisées.
Exemple : Comme une liste de clients VIP.
denylist
Liste des actions toujours interdites.
Exemple : Comme une liste noire.
motif sensible
Fichier contenant des secrets. Toujours une demande.
Exemple : .env avec des mots de passe.
session
Période où l'utilisateur utilise l'agent.
Exemple : Comme une conversation qui dure 1 heure.
scope
Type de permission : fichier, commande, URL.
Exemple : Permission pour un fichier ou une commande.
sandbox
Cage technique qui limite les actions. Vibe n'en utilise pas.
Exemple : Comme une prison pour un programme.
ADR
Document qui explique une décision technique.
Exemple : ADR 0004 explique le contrat des outils.
tool contract
Règles que chaque outil doit respecter.
Exemple : Comme un contrat de travail.
edge case
Cas rare ou compliqué.
Exemple : Comme un chemin avec ...

Points importants à retenir

1

Le serveur vérifie tout. Les clients ne décident pas.

2

Chaque outil doit déclarer ses besoins en permissions.

3

La liste de refus prime sur la liste d'autorisation.

4

Un refus n'arrête pas l'agent. Il continue son travail.

5

Vibe demande la permission. Il n'isole pas techniquement.
