📌 Vue d'ensemble

Ce répertoire implémente le système qui transforme les instructions de l'IA en actions concrètes : lecture/écriture de fichiers, exécution de commandes shell, appels à des APIs externes — avec un contrôle d'accès granulaire.

Sans ce système, Mistral Vibe serait un simple chat sans capacité d'action. Les outils sont le pont entre le raisonnement de l'IA et l'environnement d'exécution.

🏗️ Architecture

🧬

BaseTool[A, R, C, S]

Classe mère générique avec 4 paramètres de type :

  • ToolArgs : args validés par Pydantic (ex: ReadFileArgs)
  • ToolResult : résultat yieldé (ex: ReadFileResult)
  • ToolConfig : config (permission, allowlist, denylist)
  • ToolState : état persistant entre appels
run(args, ctx) -> AsyncGenerator[ToolStreamEvent | ToolResult]
get_name() : ReadFile → "read_file"
🎯

ToolManager

Le registre central :

  • available_tools → dict[str, type[BaseTool]]
  • get(name) → instance lazily créée et cachée
  • get_tool_config(name) → config effective
  • Découverte multi-sources + sélection par selection_priority
🛡️

PermissionStore

3 niveaux de permission :

ALWAYS NEVER ASK
  • allowlist / denylist : préfixes de commandes
  • sensitive_patterns : fichiers sensibles (**/.env)
  • ApprovedRule : règles de session avec wildcards ("git status *")
  • Workspace : restriction aux dossiers de confiance

⚡ Générateur asynchrone (streaming)

Chaque run() est un AsyncGenerator qui yield des valeurs une par une. invoke() valide les args (Pydantic) puis consomme ce générateur.

Deux types de yield

TypeClasse (types.py)Quand ?Exemple
ToolStreamEvent tool_name, message, tool_call_id Pendant l'exécution "Discovered AGENTS.md"
ToolResult spécifique à l'outil (ex: ReadFileResult) Une seule fois, à la fin ReadFileResult(content=..., num_lines=42)

🔍 Découverte des outils — pas à pas

  1. Chemins de recherche (_compute_search_paths) :
    • DEFAULT_TOOL_DIR = VIBE_ROOT/core/tools/builtins
    • config.tool_paths (depuis vibe_schema.py)
    • harness_files.project_tools_dirs = .vibe/tools/ par projet
    • harness_files.user_tools_dirs = ~/.vibe/tools/
  2. Scan : chaque dossier → glob("*.py"), ignore les fichiers _*, charge le module, extrait les classes BaseTool[...]
  3. Sélection : si même nom, selection_priority (défaut 0) décide
  4. Registre : available_tools → {"read_file": ReadFile, ...}
  5. Instanciation : get(name) → from_config() + cache

🛡️ Permissions — règles réelles de Bash

Les listes par défaut dans bash.py (_get_default_allowlist, _get_default_denylist) :

Allowlist (→ ALWAYS)

cd, echo, git diff, git log, git status, tree, whoami
+ ~30 commandes read-only : ls, cat, grep, pwd, find, head, wc, diff, du, file, stat...

Denylist (→ NEVER)

vim, nano, vi, emacs, bash -i, sh -i, tmux, screen, gdb, pdb, passwd
denylist_standalone : python, python3, ipython (seuls)

Sensitive patterns (fichiers → ASK même si ALWAYS)

**/.env, **/.env.*, **/.envrc, ...
CommandeVerdictPourquoi
git statusALWAYSdans allowlist
ls -laALWAYSls est read-only
cat .envASKcat allowlist MAIS .env = sensitive
vim file.txtNEVERvim dans denylist
python (seul)NEVERdenylist_standalone
python script.pyASKpas standalone, pas allowlist

📝 Système de prompts (17 fichiers .md)

Chaque outil builtin a un .md dans builtins/prompts/ qui décrit son usage pour le LLM. Chargé via get_tool_prompt() (caché avec functools.cache) :

prompt_path = class_path.parent / "prompts" / f"{class_path.stem}.md"
return read_safe(prompt_path).text

La description envoyée au LLM = ce .md (ou description ClassVar si pas de .md).
