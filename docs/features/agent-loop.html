Agent Loop
01 Overview

One async generator runs every turn

The agent loop is the engine of Mistral Vibe. It takes a user message, calls the model, runs the tools the model asks for, and repeats until the model answers in plain text. Each change of state becomes a typed event that it yields to whoever is listening: the Textual CLI, the Rust TUI through the app server, ACP clients, or a test.

4,084
lines in _loop.py, almost all in one class
16
event types the loop yields, plus the hook event family
6
middleware types checked before every model call (3 only when a limit is set)
440
test functions across 32 agent-loop test files

What the loop owns

ADR 0003 splits responsibilities cleanly. The loop owns model and tool execution. The app server owns session lifecycle and delivery to clients.

“Typed events keep UI rendering, protocol translation, logging, and tests from reaching into agent-loop internals.”

ADR 0003,

Concretely, AgentLoop.act() () returns AsyncGenerator[BaseEvent, None]. Inside one call it:

  • keeps the conversation in self.messages and saves it after every model step;
  • runs the middleware pipeline that enforces turn, price and token limits and triggers compaction;
  • executes tool calls concurrently and decides, per call, whether it may run;
  • pauses on approvals and questions, one prompt at a time, while tools already running carry on;
  • records a checkpoint so the turn can be rewound.

How to read this report

Start with Turn lifecycle for the mechanics, then Permissions and limits for the two policy layers. Event vocabulary is a reference. Every path:line link opens the source on GitHub at the pinned commit.

03 Turn lifecycle

From act() to the final answer

A turn starts with one user message and ends when the model replies without calling a tool. In between, the loop runs as many model steps as the model needs: each step is one model call followed by the tools it requested.

Guard the entry

AgentLoop.act() ·

Before anything is appended to the conversation, act() refuses work it cannot do safely:

  1. Images sent to a model without image support raise ImagesNotSupportedError ().
  2. A second concurrent turn raises AgentLoopStateError ().
  3. A running holder, such as a directory relocation, also blocks the turn (). The comment explains why: a turn starting mid-move would bind tools to a directory being moved.
  4. Backends whose close was deferred during the previous turn are closed now ().
  5. An _ActiveTurn records the turn-scoped subagent runner, tool I/O and retry sink ().
  6. History is cleaned and a checkpoint is created ().

Two nested finally blocks seal the checkpoint and clear _active_turn however the turn ends, including on cancellation ().

Emitsnothing yet

Open the user turn

_open_user_turn() ·

  1. The message is appended to self.messages and stats.steps is incremented ().
  2. UserMessageEvent is yielded ().
  3. If the message invokes a skill, its content is injected ().
  4. Files mentioned with @ are injected ().
  5. An auto-title supplied by the client is applied once ().
  6. The post-agent hook retry counter is reset.

An injected message (a retry queued by a hook, for example) takes a short path: it is appended silently and no event is emitted.

EmitsUserMessageEventSessionTitleUpdatedEvent

Check middleware

_conversation_loop() ·

At the top of every model step, not only the first, the loop asks the pipeline for a verdict and acts on it in _handle_middleware_result() ():

  • STOP: yield an assistant message wrapped in the stop tag with stopped_by_middleware=True, then return.
  • COMPACT: run compaction, then carry on with the model call.
  • INJECT_MESSAGE: append a hidden user message (a context warning, the plan-mode reminder).
  • CONTINUE: nothing.

See Permissions and limits for the six middlewares and how the pipeline combines them.

EmitsAssistantEventCompactStartEventCompactEndEvent

Call the model

_perform_llm_turn() ·

With streaming on, _stream_assistant_events() () turns each backend chunk into events as it arrives:

  • reasoning text becomes ReasoningEvent;
  • answer text becomes AssistantEvent;
  • a tool call whose name is known becomes an early ToolCallEvent, de-duplicated by id, so the UI can show it before arguments finish streaming.

Without streaming, _get_assistant_event() () makes one call and yields a single AssistantEvent, only if it has content.

A ContextTooLongError here is caught by the conversation loop and may trigger reactive compaction ().

EmitsReasoningEventAssistantEventToolCallEvent

Resolve tool calls

·

The last assistant message is parsed, then each tool call is matched against the ToolManager and its arguments validated. The result has two lists:

  • tool_calls: valid, typed ResolvedToolCalls;
  • failed_calls: unknown tools or invalid arguments.

If both are empty the model answered in text and the step ends. Otherwise _handle_tool_calls() () first reports each failed call as a ToolResultEvent with an error and a tool response message so the model sees the mistake, then yields the final ToolCallEvent for each valid call with its parsed arguments and UI presentation.

EmitsToolResultEventToolCallEvent

Run the tool batch

_run_tools_concurrently() ·

  1. Refuses to start if a batch is already active ().
  2. Creates one asyncio.Queue and binds the interaction broker to it (), so approval requests from any tool flow into the same stream.
  3. Starts one task per call () and a monitor that pushes a None sentinel when all have finished.
  4. Yields events from the queue in the order they arrive, which is completion order, not call order.

If the consumer stops iterating (GeneratorExit) or the turn is cancelled, unfinished tasks are cancelled. On cancellation the loop also awaits them so their cleanup runs ().

Emitswhatever the tools emit, see step 07

Execute one tool

_execute_tool_call() ·

  1. Instantiate the tool; a failure becomes an error result ().
  2. Serialise the input for hooks; a failure becomes an error result.
  3. Pre-tool hooks can deny the call or rewrite its input ().
  4. Permission: _should_execute_tool() returns a ToolDecision. A skip ends here with a skipped result.
  5. Invoke (): snapshot the files the tool will touch into the checkpoint, iterate tool.invoke() (yielding each ToolStreamEvent), then build a ToolResultEvent with duration, decision and approval source.
  6. Post-tool hooks may replace the text the model will see, then the tool response message is appended.

Exceptions are converted, never propagated, except cancellation, which is reported and then re-raised. See Errors and recovery.

EmitsApprovalRequestEventUserInputRequestEventToolStreamEventToolResultEventHookEvent

Close the step

Back in _perform_llm_turn(), plan-mode tool calls produce PlanReviewRequestedEvent and PlanReviewEndedEvent, and a profile switch made by a tool produces AgentProfileChangedEvent (). Then the conversation loop:

  1. increments stats.steps, which the turn limit reads (); a step retried after overflow never reaches this line, so it is not counted;
  2. saves messages to the session log ();
  3. schedules title generation after each step rather than at turn end, because one tool-heavy turn can run for minutes ();
  4. clears the context if a plan was just accepted, then loops again ().
EmitsBackgroundWorkEventSessionTitleUpdatedEventContextClearedEventAgentProfileChangedEvent

Continue or stop

The loop computes should_break_loop = last_message.role != Role.tool and not drained. In words, it runs another model step when either:

  • the last message is a tool result, so the model has to read it; or
  • pending injected messages were just drained into the conversation. At the pinned commit the only source is plan review: if the user edited the plan file while reviewing it, its new content is queued as a hidden message ().

It returns immediately if a tool result in this step was marked cancelled, which is what is_user_cancellation_event() checks (). That happens when the user interrupts at an approval prompt. When it is about to break, post-agent hooks run (); a hook can return a user message, which is appended and starts another step. The outer finally saves messages one last time ().

EmitsHookEvent

What “turn” means in the counters

stats.steps goes up once for the user message and once per completed model step. TurnLimitMiddleware stops when steps - 1 >= max_turns, so max_turns caps model steps per session, not user messages.

06 Permissions and limits

Two policy layers

Middleware decides whether the model may be called again. Tool permissions decide whether each tool call may run. Neither layer knows about the other.

Tool permissions: first match wins

Pre-tool hooks run first and can deny the call outright. Then _should_execute_tool() () walks this ladder under the permission store’s lock:

  1. 1

    Bypass

    If bypass_tool_permissions is set, every call runs.

    executeapproval_source=bypass
  2. 2

    Resolve the permission

    The tool may compute a permission from its arguments with resolve_permission(args). The bash tool uses this to classify commands, and file tools use it to check paths. If it returns nothing, the configured permission for that tool is used.

    no outcome yet
  3. 3

    ALWAYS

    Configured or resolved as always allowed.

    executeapproval_source=config
  4. 4

    NEVER

    Disabled. The model receives the reason as feedback.

    skipapproval_source=never
  5. 5

    Smart approval

    Otherwise, if the call lists required permissions and the session’s PermissionStore already covers every one of them (the user chose “always allow” earlier), it runs.

    executeapproval_source=smart
  6. 6

    Ask the user

    _ask_approval() () asks the broker for the uncovered permissions only. Any answer other than YES skips the call.

    execute or skipapproval_source=user

How an approval round-trip works

  1. The broker creates a request_id and an asyncio.Future, and puts an ApprovalRequestEvent on the batch queue ().
  2. The tool task awaits the future. Tools that already passed their permission check keep running.
  3. The client calls resolve_approval_request(request_id, response, feedback) (), which sets the future’s result.
  4. reject_request() sets an exception instead. The app server uses it when it cancels its pending callbacks ().

One prompt at a time

_should_execute_tool() holds the PermissionStore lock while it waits for the user. Approval prompts in a batch are therefore serialised, and a tool that reaches its permission check while a prompt is open waits too, even one that would be auto-approved. test_parallel_approval_requests_are_serialized asserts this (). Only bypass_tool_permissions skips the lock.

Outside a batch

When no queue is bound, request_approval() returns NO with “Tool execution not permitted.”, and request_user_input() raises ToolError. A tool cannot block on a user who is not there.

Middleware: checked before each model call

Built in _setup_middleware() () in this order. The first three exist only when their limit is set.

MiddlewareConditionActionSource

Combination rule (): the pipeline runs middlewares in order and returns the first STOP or COMPACT immediately. Injected messages from the others are joined with a blank line into one hidden user message. A limit therefore always wins over a warning.

07 Errors and recovery

Tool failures stay inside the turn

The loop draws a sharp line. Problems with a request are raised to the caller before anything changes. Problems with a tool are turned into results the model can read and react to.

FailureWhere it is handledWhat happensTurn
ImagesNotSupportedErrorRaised to the caller before the message is appended.never starts
AgentLoopStateErrorA turn or holder is already active. Raised, no state change.never starts
ContextTooLongErrorCompaction, then the same step is retried. Allowed once per turn; re-raised in strict mode.recovers
Unknown tool or bad argumentsError result plus a tool response so the model can correct itself. Counts as failed.continues
Tool cannot be instantiatedError result.continues
Pre-tool hook denialDenial result; the tool never runs.continues
ToolPermissionErrorError result. The call moves from agreed to rejected in the stats.continues
ToolError, any ExceptionError result with a separate error_display for the UI; post-tool hooks still run. Counts as failed.continues
asyncio.CancelledErrorResult with cancelled=True, cleanup through _finalize_cancelled_tool(), then re-raised.aborts

Reactive compaction

_should_self_heal() () is two conditions: recovery not yet used in this turn, and raise_on_compaction_failure off.

The flag is reset at the start of each turn (). A second overflow in the same turn propagates, which prevents a compact-and-retry loop.

Cancellation points

  • Interrupt at an approval prompt: the answer carries a cancellation message, so the skipped result has cancelled=True. The loop saves the step and returns without calling the model again (test_act_handles_user_cancellation_during_streaming).
  • Plain denial: a skipped result without cancelled; the model is called again and sees the refusal.
  • Task cancelled by the client: asyncio.CancelledError reaches the tools, each yields a cancelled result, and the error propagates out of act() through the finally blocks that save and seal.

State stays consistent

  • Checkpoint created at entry, sealed in finally.
  • Files a tool will change are snapshotted before it runs.
  • Messages are saved after every step and again in finally.
  • Every tool call gets a tool response, even on failure, so the history stays valid for the next model call.
08 Integration

What plugs into the loop

Most subsystems reach the loop in one of two ways: through InvokeContext, which every tool receives, or through hooks around tool calls and turns.

What a tool receives

InvokeContext is built per call in _invoke_tool() (). Its fields show what tools are allowed to do:

FieldLets a tool…
interaction_requestsask for approval or user input (the broker).
subagent_runnerrun a child agent loop (the task tool).
switch_agent_callbackchange the active agent profile (leaving plan mode).
request_clear_context_callbackclear history after a plan is accepted.
sampling_callbackcall the model itself (MCP sampling).
permission_storeread and record session approvals.
skill_manager, is_skill_loadedload skills without duplicating them.
mcp_pool, tool_ioreach MCP servers and client-provided I/O.
session_dir, scratchpad_dir, plan_file_pathknow where to write.

Subagents

The task tool receives a SubagentRunnerPort () and runs another AgentLoop. SubagentRunAccumulator () turns the child’s events into ToolStreamEvents for the parent and builds the final TaskResult. Subagents inherit the parent’s session approvals and share its approval lock ().

Hooks

Three HookTypes (). pre_tool can deny or rewrite input; its events are buffered because it is meant to be quick. post_tool can replace the text the model sees. post_agent runs when the turn would end and can return a user message that starts another step.

Compaction

compact() () delegates to CompactionManager, which appends the summary as a hidden user message marked context_boundary="compaction" and resets context_tokens (). The full history stays in the session; only what follows the boundary is sent to the model. The session id does not change, so the two ids on CompactEndEvent are equal. Telemetry records the outcome (success, failure, cancelled) in a finally.

Sessions and rewind

SessionLogger persists messages and stats. CheckpointRecorder brackets each turn and collects the file snapshots tools add, which is what lets rewind restore files as well as messages.

Configuration

The loop reads a layered VibeConfigSchema through ConfigOrchestrator. max_turns, max_price and max_session_tokens are constructor arguments that feed the middlewares; max_tokens is passed to the backend as the per-response limit. set_max_turns() rebuilds the middleware pipeline.

Telemetry and experiments

The loop sends new_session, ready, session_closed, auto_compact_triggered, request_sent and tool_call_finished events, and wraps each turn in an agent_span and each tool in a tool_span for tracing. Feature flags come from ExperimentManager, whose attributes also decide the reported user_plan.

Coverage

Covered

  • Tool execution paths: success, denial, skip, errors, and parallel batches, including serialised approvals and call events emitted before results
  • Reactive compaction, including strict mode (test_reactive_compaction_disabled_in_strict_mode) and the turn budget after overflow
  • Interrupting at an approval prompt, and cancellation before and during tool execution
  • Plan-mode middleware, auto-compaction, context warnings, token limit
  • reject_request() from the app server side ()
  • Plan mode, hooks and teleport end to end

Thinner

  • A second overflow in the same turn (the “once per turn” rule): every reactive test overflows only once.
  • PriceLimitMiddleware has no unit test; TurnLimitMiddleware is only exercised inside a compaction test.
  • The pipeline’s combination rule (first STOP/COMPACT wins, injections are joined) is not tested with several middlewares at once.
  • An auto-approved tool waiting on the permission lock while another tool’s prompt is open.

Code quality

Strengths

  • Strict typing throughout: Pydantic events, ToolDecision, literal types for approval sources.
  • Comments explain why, not what (the holder check, the per-step title scheduling, the turn budget).
  • Cleanup is structural: nested finally blocks, queue unbinding, task cancellation.
  • Ports (SubagentRunnerPort, InteractionRequestPort) keep tools testable without a loop.

Weaknesses

  • AgentLoop is a 3,500-line class whose noqa: PLR0904 (too many public methods) admits it. Plan mode, teleport and title generation could be collaborators.
  • Turn state is spread over _active_turn, _holders, _tool_event_queue and flags like _reactive_recovery_used; an explicit state object would make invariants checkable.
  • _conversation_loop() needs noqa: PLR0912 (too many branches).
  • An unused event type (TokenUsageUpdatedEvent) remains in the public vocabulary.
10 Design decisions

Why it is built this way

Five decisions shape the loop. Each is weighed here against what it costs.

An async generator as the only interface

· ADR 0003

Reasoning

The caller pulls events at its own pace, so the CLI, ACP and tests consume exactly the same stream. Cancelling the consumer cancels the turn, because GeneratorExit propagates into the tool batch.

Trade-offs

  • One interface for every surface
  • Natural backpressure
  • Answering approvals needs a side channel (resolve_approval_request())
  • Every exit path must clean up in finally

Typed events instead of callbacks

ADR 0003,

Reasoning

“Prefer adding or extending typed events over adding surface-specific callbacks into the agent loop.”

Trade-offs

  • Clients cannot reach into internals
  • Tests assert on event sequences
  • Unused events linger
  • Compaction rides on tool_call_id as an ACP workaround

Concurrent tools through one queue

Reasoning

Tool calls in one model response are usually independent reads, so running them in parallel cuts latency. The single queue also carries approval requests to the client. Permission checks, however, run under one lock, so the user answers one prompt at a time.

Trade-offs

  • Lower latency for independent calls
  • Never two approval prompts at once
  • Results arrive in completion order
  • An open prompt also delays tools that would be auto-approved
  • Two calls that touch the same file are not serialised by the loop

Middleware for limits and reminders

Reasoning

Each concern is a small class with one before_turn(); the loop only interprets four actions. Plan mode reuses the same mechanism to inject its rules.

Trade-offs

  • Easy to add a limit
  • Unit-testable in isolation
  • Runs before model calls only, never before a tool
  • Order matters but is implicit in _setup_middleware()

Reactive compaction, once per turn

Reasoning

Token estimates can be wrong, so proactive compaction alone is not enough. When the provider still rejects the context, compacting and retrying keeps the conversation alive without user action.

Trade-offs

  • Overflow is invisible to the user
  • A retried step does not consume turn budget
  • Detail is lost in the summary
  • The step costs an extra model call
11 Open questions

What we checked, and what is still open

The first draft of this report listed ten open questions. Reading the code answered three of them.

1

Is TokenUsageUpdatedEvent used? answered

No. Nothing under vibe/ constructs it at the pinned commit ().

2

How does WaitingForInputEvent relate to the loop? answered

It is a delivery-layer event built by the app server projector (), not by the loop.

3

When does reactive compaction run? answered

When recovery has not been used in the current turn and raise_on_compaction_failure is off ().

4

How does the session lease interact with turns? open

SessionLease is passed to the constructor; its use during a turn was not traced.

5

What happens to self.messages when a stream fails midway? open

Whether a partial assistant message is kept or rolled back depends on _chat_streaming() (), which was not read in full.

6

Are concurrent writes to the same file safe? open

The loop runs all calls of a step in parallel and does not order them. Whether tools lock files themselves was not checked.

7

How does teleport fit the turn lifecycle? open

teleport_to_vibe_code() () and its end-to-end test exist; the flow was not traced.

8

Are backend closes bounded in long sessions? open

The module-level _pending_close_tasks set () holds references until each close finishes. The set looks self-cleaning; its behaviour under a failing close was not checked.

9

What are the semantics of a checkpoint while streaming? open

Created at entry and sealed at exit; whether a rewind mid-turn is possible was not verified.

10

When do the experimental flags graduate? open

experimental_enable_registry_skills and experimental_enable_model_catalog gate features with no visible roadmap in the repository.
